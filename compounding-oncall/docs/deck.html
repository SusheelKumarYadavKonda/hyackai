The problem

The knowledge exists. It just isn't actionable.

A column gets renamed in an upstream CDC source. Three hops downstream a mart starts producing nulls, a job fails its NOT NULL assertion, and someone on‑call spends 45 minutes rediscovering a causal chain a colleague already traced last month.

The postmortem gets written. It goes in a wiki. Nobody reads it. Six weeks later a different table fails the same way and the 45 minutes are spent again.

From our own synthetic corpus — pm_inventory_repeat.md: “The fix was already written down. The cost was not the diagnosis, it was that nobody could find the previous diagnosis.”
Agents that are smart once and forgetful forever. That is the gap we set out to close.

What we built

A real trigger, not a simulated one

scripts/run_job.py --table orders          a genuine subprocess
  reads Parquet, asserts NOT NULL + row-count minimums
  fails → real stderr, exit 1
        │
        ▼
supervisor catches returncode != 0, captures stderr verbatim
        │
        ▼
signature(error_text)   strip timestamps, paths, counts, table name
        │
        ▼
   muscle memory: seen this shape before?
   ├── HIT  → replay the captured path · 0 tokens · skip to verify
   └── MISS → lineage · cognee · hydradb · hotdata · rocketride
        │
        ▼
verify: re-run the real job, expect exit 0
        │
        ▼
learn: capture path · record outcome · write narrative back
Both the trigger and the verify are real processes. PASS means a subprocess exited 0 — not that the agent asserted success.

Architecture

Five layers, five different questions

Muscle

Signature‑keyed path store. A hit is a dict lookup — which is why replay is zero tokens, not fewer.

Cognee

Runbooks and postmortems → knowledge graph. What the org knew before we started.

HydraDB

Accumulating resolution memory. What we have learned since.

hotdata

Live SQL over the warehouse. What is wrong right now. Never cached.

RocketRide

Chains the remediation: quarantine → rerun → notify. Acts.

Why three memory layers

They answer questions on different time horizons, so action selection is a precedence chain: a fix we have proven beats a fix the runbooks prescribe beats a built‑in heuristic. Recall that never changes a decision is decoration; ours decides.

Hard boundary: no Parquet‑derived number is ever written to a memory layer. Null rates go stale in hours; lineage is stable for weeks.

Engineering

What the docs said, and what was actually true

Three of four vendors behaved differently from their documentation. Each was found by running against the live API, and each is recorded in docs/03_SDK_NOTES.md.

HydraDB · no Cypher

The spec's centrepiece was a 3‑hop graph query. HydraDB v2 has no graph query language at all, so the lineage graph became ours, traversed in Python. HydraDB became the accumulator instead.

hotdata · silent 404

A load reporting row_count=20000 still 404'd on query, because the catalog is always default regardless of the alias you set. Success then failure, with no obvious link.

Cognee · list, not string

datasets as a bare string works locally and returns 422 remotely. Hosted responses also wrap per dataset, so unwrapping was needed or every excerpt was raw JSON.

Rote · no docs

Priority #1 in the fallback order with no published API. We implemented muscle memory ourselves — 90 lines, no network. The load‑bearing claim cannot depend on an unverified SDK.

A test caught the one bug that would have killed the demo: the table name is embedded in real job output (job_orders_daily, in orders:), so keeping it out of the hash input was not enough. Without that fix nothing ever replays and there is no curve.

Honesty

What is real, and what we would say if asked

  • All four vendor services run live. Cognee on a hosted tenant, HydraDB accumulating real memories, hotdata computing over uploaded Parquet, RocketRide chaining three steps on staging. The UI header shows REAL or STUB every run — we cannot demo stubs by accident.
  • Muscle memory is ours, not a vendor. ~90 lines, JSON on disk. Said plainly because it reads as discipline, not omission.
  • Token counts on any stubbed layer are estimates, computed from real serialised context size and labelled as such in the report footer.
  • Every layer keeps a working stub behind a config flag. Any vendor can be dropped with one flag and the demo still runs end to end at 7.4×.
  • Incident 1 is genuinely cold. Both memory stores are cleared at start, and HydraDB's delete lag is filtered — so the first incident cannot read its own predecessors.
